## 二、数据模型设计

### 2.1 WeiboPost（微博数据）

```sql
CREATE TABLE weibo_posts (
    id              INTEGER PRIMARY KEY,
    post_id         TEXT UNIQUE NOT NULL,        -- 匿名哈希 ID
    text            TEXT NOT NULL,                -- 清洗后正文
    raw_text        TEXT,                         -- 原始正文
    published_at    DATETIME NOT NULL,            -- 发布时间
    offset_min      REAL,                         -- 相对发震的分钟偏移
    
    -- NLP 处理结果
    ner_locations   JSON,                         -- [{name, lng, lat, confidence}]
    sentiment       VARCHAR(20),                  -- urgent/negative/neutral/hopeful
    damage_type     VARCHAR(30),                  -- 人员伤亡/房屋倒塌/道路中断/...
    keywords        JSON,                         -- 命中关键词列表
    severity_vote   INTEGER,                      -- 1-5 严重度
    credibility     REAL DEFAULT 0.5,             -- 可信度评分 0-1
    
    -- 状态
    source          VARCHAR(50) DEFAULT '微博',
    is_filtered     BOOLEAN DEFAULT FALSE,        -- 是否被噪声过滤
    filter_reason   VARCHAR(100),                 -- 过滤原因
    processed       BOOLEAN DEFAULT FALSE,        -- NLP 是否已处理
    processed_at    DATETIME,
    
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 2.2 DisasterHotspot（灾情热点）

```sql
CREATE TABLE disaster_hotspots (
    id              INTEGER PRIMARY KEY,
    location_name   TEXT NOT NULL,                -- 地名
    longitude       REAL NOT NULL,
    latitude        REAL NOT NULL,
    
    -- 聚合统计
    post_count      INTEGER DEFAULT 0,            -- 相关微博数
    urgency_score   REAL DEFAULT 0,               -- 紧急度评分 = 频次×严重度
    max_severity    INTEGER DEFAULT 0,            -- 最高严重度
    damage_types    JSON,                         -- {"房屋倒塌": 5, "人员伤亡": 3}
    sentiment_dist  JSON,                         -- {"urgent": 3, "negative": 2, ...}
    
    -- 优先级
    priority_level  VARCHAR(10),                  -- P0/P1/P2/P3
    priority_score  REAL,                         -- 综合评分
    priority_reason TEXT,                         -- AI 生成的排序理由
    
    -- 救援状态
    has_rescue_team BOOLEAN DEFAULT FALSE,        -- 是否已有救援队
    rescue_status   VARCHAR(20) DEFAULT 'pending',-- pending/en_route/on_site/done
    
    -- 关联
    disaster_id     INTEGER,                      -- 关联 Disaster 表
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME
);
```

### 2.3 RescueCase（救援案例知识库）

```sql
CREATE TABLE rescue_cases (
    id              INTEGER PRIMARY KEY,
    case_id         TEXT UNIQUE NOT NULL,         -- C-01 ~ C-08
    name            TEXT NOT NULL,                -- 案例名称
    magnitude       REAL,                         -- 震级
    depth_km        REAL,                         -- 震源深度
    location        TEXT,                         -- 位置
    latitude        REAL,
    longitude       REAL,
    occurred_at     DATE,                         -- 发震日期
    casualties      INTEGER,                      -- 遇难/失踪人数
    
    -- 匹配维度
    terrain         VARCHAR(50),                  -- 地形：山区/高原/平原/沿海
    building_type   VARCHAR(50),                  -- 建筑类型：砖混/框架/土石/混合
    population_density VARCHAR(50),               -- 人口密度
    season          VARCHAR(20),                  -- 季节
    weather         TEXT,                         -- 天气条件
    infrastructure  VARCHAR(50),                  -- 基础设施状况
    secondary_hazard TEXT,                        -- 次生灾害类型
    
    -- 救援信息
    timeline        JSON,                         -- 救援时间线
    strategies      JSON,                         -- 关键策略
    lessons         JSON,                         -- 经验教训
    tags            JSON,                         -- 特征标签
    
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 三、核心服务流程

### 3.1 微博数据管道（愿景 2）

```
触发：ICL 预警收到任何地震信号
  │
  ├─→ 1. 关键词监测
  │     启动微博 API 轮询，关键词列表：
  │     ["地震","摇晃","塌了","被困","失联","救援","物资","伤亡",...]
  │
  ├─→ 2. 噪声过滤（4 层）
  │     Layer 1: 去重 — 正文相似度 > 0.85 → 聚合
  │     Layer 2: 辟谣 — 交叉比对官方通报，标记已辟谣内容
  │     Layer 3: 机器人 — 账号行为分析（发帖频率/模板匹配）
  │     Layer 4: 地理围栏 — NER 地名做距离过滤（震中 ±300km）
  │
  ├─→ 3. NLP 处理
  │     ├─ NER 地名提取（Qwen LLM + 地名词典 fallback）
  │     ├─ 情感分析（urgent/negative/neutral/hopeful）
  │     ├─ 损毁类型分类（6 类）
  │     └─ 可信度评分（认证媒体 0.9 > 普通用户 0.5 > 疑似机器人 0.1）
  │
  └─→ 4. 入库 + 推送
        写入 weibo_posts 表
        触发 hotspot_service 更新灾情热点
```

### 3.2 动态优先级引擎（愿景 3）

```
输入：灾情热点列表 + 呼救信号 + 救援资源
  │
  ├─→ Step 1: 基础评分
  │     urgency_score = post_count × avg_severity × credibility_weight
  │
  ├─→ Step 2: 呼救加权
  │     检测微博中的呼救关键词（"救命""被困""紧急"）
  │     呼救信号所在区域 → urgency_score × 1.5
  │
  ├─→ Step 3: 资源约束扣减
  │     已有救援队在前 → score × 0.6
  │     交通不可达（道路中断标记）→ score × 0.3
  │     超时 72h → score × 0.5（生存率骤降）
  │
  ├─→ Step 4: AI 理由生成
  │     Qwen3.8-Max 生成 ≤40 字优先级理由
  │
  └─→ Step 5: 输出 P0-P3
        P0: score >= 0.8 （立即派遣）
        P1: 0.5 <= score < 0.8 （优先派遣）
        P2: 0.3 <= score < 0.5 （常规搜救）
        P3: score < 0.3 （持续监测）
```

### 3.3 AI 决策助手（愿景 6）

```
输入：当前灾情态势快照
  │
  ├─→ Step 1: 灾情特征提取
  │     {震级, 震源深度, 地形, 建筑类型, 人口密度, 季节, ...}
  │
  ├─→ Step 2: 案例匹配（case_matcher.py）
  │     10 维加权相似度计算 → TOP 3 最相似历史案例
  │
  ├─→ Step 3: AI 综合研判（Qwen3.8-Max）
  │     输入：当前态势 + 匹配案例 + 微博分析数据
  │     输出：
  │       · 最需要优先救援的区域（附数据依据）
  │       · 推荐行动方案（参考匹配案例的救援策略）
  │       · 风险预警（次生灾害、天气变化等）
  │       · 资源调配建议
  │
  └─→ Step 4: 结构化输出
        {
          priority_areas: [...],
          action_plan: "...",
          matched_cases: [...],
          risk_warnings: [...],
          resource_suggestions: [...]
        }
```
