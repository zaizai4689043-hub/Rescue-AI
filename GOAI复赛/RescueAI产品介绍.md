# RescueAI · 社媒灾情线索智能中枢（复赛版产品介绍）

> **Physical AI for Earthquake Rescue —— 让社媒上的每一句呼救，都被核实、被推送、被闭环。**
>
> **产品定位：本平台不自建救援队伍，而是作为社媒灾情线索的智能中枢——通过 AI 初筛＋值班人员多源核实，将有效线索第一时间推送至属地公益救援队，并全程追踪反馈，确保每条线索都有追踪、有反馈、有闭环。**
>
> **责任声明：RescueAI 仅提供辅助决策与线索中转，不替代专业救援判断，不下达行动指令。**
>
> 本文档以复赛版 `semifinal.html`（在线地址 https://deploy-eight-mocha-43.vercel.app/semifinal.html ）为唯一基准，所述功能与流程均经源码逐条核验。

## 一、问题：黄金 72 小时，呼救很多、回音很少

地震救援存活率随时间急剧下降：震后 24 小时约 **80%** → 48 小时约 **50%** → 72 小时约 **30%**。而最宝贵的时间窗里，信息是断裂的：

| 痛点 | 事实依据（2025-03-28 缅甸地震） |
|---|---|
| **官方通报沉默期** | 震后约 **5 分钟**社媒已在流传伤亡信息；官方首报滞后约 **5 小时** |
| **呼救碎片化** | 数万条中文微博散落呼救、损毁、谣言，无结构化、无坐标、无优先级 |
| **线索无闭环** | 一条"救命"帖发出后，**没有人核实、没有人对接、没有人反馈**——呼救石沉大海 |

**一个关键细节：** 首条涉震微博**早于主震发震时刻 1 分 46 秒**。社交媒体是最快的"第一传感器"，但今天它停在"被看见"，没有走到"被回应"。

> **RescueAI 要补的不是"看见"，而是"回音"：让每一条呼救都被核实、被推送、被闭环。**

## 二、定位：不自建救援队伍的"智能中枢"

> **RescueAI 是社媒灾情线索的智能中枢：AI 初筛 ＋ 值班人员多源核实 → 有效线索推送属地公益救援队 → 全程追踪反馈。**

我们不造车，我们修路。平台**不自建救援队伍**，而是把"社媒呼救"与"属地救援力量"之间缺失的**核实与对接环节**补上：

| 角色 | RescueAI 做什么 | 不做什么 |
|---|---|---|
| 对社媒线索 | AI 初筛提取要素、评估置信度、排优先级、拦截误报 | 不轻信、不直接转发未经核实内容 |
| 对值班人员 | 提供 5 项多源核实工作台与进度追踪 | 不替代人工核实判断 |
| 对救援队 | 推送**经核实**的灾情描述与坐标、双向中转、追踪反馈 | 不自建队伍、不下达行动指令 |
| 对求助人 | 隐私保护：双向中转，不向救援队外暴露求助人隐私 | 不公开求助人身份 |

**目标用户：** 应急值班值守人员（主用户）、属地公益/社会救援力量、人道协调机构。

## 三、产品形态：一块大屏、一条实时流、三级兜底（评审维度：Demo 可运行性）

### 3.1 载体

| 载体 | 形态 | 说明 |
|---|---|---|
| **复赛版指挥中心** | `semifinal.html` 单文件，2560×1440 大屏自适应缩放 | 零构建、零第三方图表库，双击可运行 |
| **在线版** | https://deploy-eight-mocha-43.vercel.app/semifinal.html | 评委随时可访问 |
| **实时社情层** | `live_feed.py`（端口 8012，`--mode mock\|weibo`） | 可选接入微博真实通道 |

### 3.2 数据双源与三级兜底

- **实时源**：页面启动尝试连接 `127.0.0.1:8012/live/social`（3s/5s 超时）；
- **兜底链**：连接失败自动 `loadMockFallback` → 回退内置**真实缅甸社媒帖回放**（`REAL_SOCIAL_POSTS`），按节奏逐条注入（`injectNext`）；
- **地图兜底**：Leaflet 真实底图加载失败时回退 SVG 示意图。

> **可靠性结论：断网、断实时层均可完整演示，全流程不依赖任何外部 LLM API。**

### 3.3 一键演示

顶栏「▶ 一键演示」自动播放完整闭环（线索注入 → 初筛 → 核实 → 推送 → 闭环），评委无需手动操作即可看完全链路。

## 四、核心工作流：线索 → 工单 → 核实 → 推送 → 闭环（评审维度：用户流程闭环）

### 4.1 任务看板五列（全局态势）

```
📥 新情报 → ⚠ 待批准·人类权力区 → 📡 已派遣 → 🔍 待核验 → ✅ 已闭环
```

其中**「待批准·人类权力区」以橙色高亮独立成列**——所有需要人拍板的任务集中于此，机器不得越权。

### 4.2 核实闭环四阶段（点击任一社媒卡片展开抽屉）

| 阶段 | 内容 | 把关点 |
|---|---|---|
| **1. AI 智能初筛** | 从微博捕获灾情信息，自动提取**灾情类型 / 风险等级 / AI 置信度** | 机器完成，标注置信度 |
| **2. 多源核实（值班人员）** | **5 项核实**：① 私信联系发帖人 ② 电话核实 ③ 评论区询问 ④ 发帖历史回溯 ⑤ 同区域多源交叉印证；进度环实时显示 n/5 | **5 项全部完成才解锁推送按钮** |
| **3. 推送属地公益救援队** | 推送**经核实**的灾情描述与坐标；显示对接通道与预计抵达 ETA | 合规双向中转，不暴露求助人隐私 |
| **4. 追踪反馈** | 每条线索追踪至闭环（≥5 条反馈记录标记"已闭环"） | **每条线索有回音** |

### 4.3 救援工单四步

**工单生成 → 救援队接单 → 现场核实 → 救援闭环**，每步带时间戳，支撑「平均闭环时间 / SLA 达成率」KPI 度量。

### 4.4 处置方案知识库（参谋输出）

按灾型给出 A/B 双方案＋依据＋风险，例如：
- **房屋倒塌**：A 重型搜救队+生命探测仪进场 ／ B 无人机侦察+热成像搜索（附"建筑结构不稳、需防二次坍塌"等依据）；
- **道路中断**：A 工程抢险队疏通+临时便道 ／ B 空投应急物资保障基本需求。

> 注：无人机侦察、空投在此为**处置建议选项**（知识库条目），本平台不做无人机控制与物资调度。

## 五、四大 Agent：哨兵 · 研判 · 参谋 · 通讯员（评审维度：Agent 能力）

| Agent | 职责 | 状态可视化 |
|---|---|---|
| 🛰 **哨兵** | 监听微博社媒流，捕获灾情线索 | 状态卡实时闪烁 |
| ⚖️ **研判** | 多源伤亡线索真值发现、置信度评估 | 状态卡 |
| 🧠 **参谋** | 基于多源交叉验证生成简报与处置建议（决策桌） | 状态卡 |
| 📡 **通讯员** | 生成救援对接工单、推送与追踪反馈 | 状态卡 |

四 Agent 在右栏以状态卡呈现，动作触发时徽章闪烁，全程可追溯"谁在什么时候做了什么"。

**一条可验证的完整任务链路：** 哨兵捕获呼救帖 → 研判初筛（灾型/风险/置信度）→ 进入看板「新情报」→ 值班人员 5 项核实 → 「待批准·人类权力区」人工批准 → 通讯员生成工单推送救援队 → 追踪反馈 → 「已闭环」。

## 六、人机协同与责任边界（评审维度：高风险场景人工确认）

| 机制 | 实现 | 边界声明 |
|---|---|---|
| **人类权力区** | 看板独立成列「⚠ 待批准·人类权力区」，待批准数进 KPI | 机器不越权批准 |
| **核实解锁推送** | 5 项多源核实**全部完成**，"推送至救援队"按钮才解锁 | 人工核实是推送的前置条件 |
| **SLA 倒计时** | P0 **SLA 3min** / P1 **SLA 5min**，超时红色闪烁告警 | 时效压力可视化，但批准权在人 |
| **隐私中转** | 推送内容为经核实的灾情描述与坐标；**平台双向中转，不向救援队外暴露求助人隐私** | 求助人身份受保护 |
| **定位声明** | 抽屉常驻产品定位声明 | 不自建队伍、不替代专业判断 |

> **一句话：AI 负责快，人负责准；机器跑流程，人拍板。**

## 七、误报控制：拦截区（评审维度：可靠性）

- **拦截规则**：无灾情要素或疑似谣言的帖**拦截不入队列**（`priorityReason` 明确给出拦截理由）；
- **拦截区**：社媒情报流底部折叠「▼ 拦截区 (N)」，逐条展示被拦截帖与拦截理由，可展开审计；
- **拦截点图层**：地图上单独图层标注拦截点位置；
- **误报拦截数 KPI**：顶栏 KPI 卡实时计数。

> **边界声明：** 拦截为工程过滤规则，**不等于谣言查全率**；与官方通报交叉验证仍为最终防线，不编造、不夸大。

## 八、技术实现（评审维度：技术实现）

| 层 | 实现 |
|---|---|
| **前端架构** | 单文件 HTML + 原生 JS；2560×1440 基准 CSS Grid 三栏布局，等比缩放适配 |

| **简报/方案** | 参谋决策桌基于任务池聚合生成简报；灾型→A/B 处置方案知识库 |
| **实时接入** | 可选 `live_feed.py:8012`（mock / weibo 双模式），超时自动降级 |
| **外部依赖** | **零 LLM API 依赖**——断网、断密钥均全流程可演示 |

## 九、可靠性与度量（评审维度：评测结果）

| 指标 | 说明 |
|---|---|
| **SLA 分级** | P0 = 3min ／ P1 = 5min，倒计时可视化（normal/urgent 两态） |
| **KPI 四卡** | 平均闭环时间 ／ SLA 达成率 ／ 误报拦截数 ／ 待批准数 |
| **影响统计** | 界面呈现：影响区县 **6 个** ／ 影响人数 **385 万人** ／ 经济损失 **82 亿元** |
| **降级链** | 实时层失败→内置真实帖回放；Leaflet 失败→SVG 示意图；全程零外部 LLM 依赖 |
| **闭环度量** | 工单四步时间戳 → 平均闭环时间可计算 |

> **如实披露：** 本版度量（SLA 达成率、平均闭环时间）为**演示态自计量**，样本为内置真实社媒帖回放与推演工单；定位采用地名词典法，**无发帖真实定位 ground truth，定位准确率不予承诺**。桌面演练需真实应急人员执行，**尚未开展，不表述为已验证**。
