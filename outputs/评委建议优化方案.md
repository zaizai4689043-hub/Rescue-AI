# RescueAI 评委建议优化方案（复赛窗内落地版）

> 编制日期：2026-08-29 ｜ 依据：复赛评委三条优化建议 + Task #8 盘点报告（能力-验证状态矩阵 / UI 标注盘点 / 可靠性度量盘点 / 人工确认机制盘点）
> 口径基准：《数据来源与合规说明.md》（V1.1）、《backend/Qwen 初版/演示须知.md》、《outputs/评测指标.md》、`.ppt_build/_semifinal_slides.py`（口径页）——本方案全部文案复用上述既有措辞，不新造口径。

## 背景

**评委三条建议（原文归纳）：**

1. **真实能力与演示边界透明化**——区分「真实数据验证 / 历史重演 / 仿真动画」三类能力，并在界面明确标注；
2. **应急信息可靠性验证**——社媒时效、定位准确率、误报控制三项可靠性关切；建议以真实应急人员桌面演练证明辅助决策价值；
3. **人工指挥责任边界**——系统仅辅助建议、不替代人工指挥；需有关键决策的人工确认与升级机制。

**目标：** 在复赛体验包到期前的时间窗内，用 ≤2–3 人日的总量把三条建议转化为**可检查的界面标注、可复跑的度量产物、可执行的演练工具包**；超出窗口的项明确排期（P1/P2）与对外口径，防过度承诺。

**时间窗约束（硬约束）：**

- 微博官方通道 7 天免费体验包**有效期至 2026-09-04**（开发者认证 2026-08-28 通过，见合规文档 §二.6/§三.4）；凡依赖真实 weibo 调用的度量（WP9）必须在此日期前完成采样，到期后系统自动降级至缓存/数据集回放，服务不中断。
- 本方案 P0 总量 **2.9 人日**，全部为「纯文案标注 + 离线回测脚本 + 既有字段口径化」，不引入新外部依赖、不改动演示主流程逻辑。

**事实核查备注（与任务输入的两处出入，已按仓库实际修正）：**

- `labels.json`（52 条人工标签）实际位于 `backend/Qwen 初版/data/labels.json`（dict 结构：`post_id → {damage_type, sentiment}`），不在 `work buddy接力/data/`（该目录仅有 `rescue_cases.json`）；
- `_weibo_probe.json` 实际存在于 `backend/Qwen 初版/data/_weibo_probe.json`（历史微博检索接口响应快照，无时间链与元数据，不作为探针链证据）；weibo-cli 实调证据以 `outputs/weibo_probe/` 下的 7 份探针记录（01_version…06_search_error.txt）为准，WP9 基线采样以体验期内重新实调并留档为准。

**全局工程约定（适用于所有 UI 类改动）：**
`backend/Qwen 初版/代码1.2-ai.html` 与 `deploy/index.html` 经 `cmp` 验证**字节级一致**（盘点报告关键事实），一切界面改动**必须双文件同步**，验收以 `cmp` 通过 + 既有回归脚本全绿为准（盘点报告行号引用对两文件通用）。`frontend/src`（Vue 标准平台）当前免责/模式标签/演示声明 0 命中，本窗内不纳入改造，列入 P2。

- **具体改动**：`代码1.2-ai.html` 与 `deploy/index.html` 顶栏指挥栏右侧新增持久徽标组件，按 URL 参数三态切换（含叠加态）。文案草案（直接落地）：

| 状态 | 徽标文案 | 样式建议 |
|---|---|---|
| 默认（无参数） | `LIVE · 真实数据流（离线自动兜底）` | 绿 |

## 二、方向②：应急信息可靠性验证

> 盘点结论（报告 E.②）：三方向中缺口最大——无定位准确率/误报率/召回率指标与混淆矩阵、无信息时效指标（weibo 真实帖 offset_min 恒为 null）、无桌面演练；**但 `labels.json` 提供了立即可用的回测素材**，漏斗统计与时效字段已就绪只差口径化。

### 措施 2.a 分类回测：52 条人工标签 × nlp_service 混淆矩阵

- **现状差距**：盘点报告 C 节——`nlp_service.py` 损毁类型/情感=关键词计数，**无准确率评估代码、无混淆矩阵产物**；评测指标报告无任何 precision/recall/F1 数字；而 `backend/Qwen 初版/data/labels.json` 已有 52 条人工标签（damage_type + sentiment），回测素材现成。
- **具体改动**：
  1. 新增脚本 `backend/Qwen 初版/scripts/backtest_classification.py`（仅标准库）：读 `data/social_posts.json`（52 条正文）+ `data/labels.json`（人工标签），对每条调用与线上同源的关键词分类逻辑（从 `nlp_service.py` 复用同一词典/规则，保证「测的就是演示用的那套」），输出 `damage_type` 与 `sentiment` 两个维度的混淆矩阵、precision / recall / F1（宏平均 + 逐类），落盘 `data/backtest_report.json` 并打印 Markdown 表格；
  2. `outputs/评测指标.md` 新增 §2.5「分类回测（52 条人工标签）」章节：贴矩阵与 P/R/F1，附样本量与类别不均衡说明（复用 `data/README.md` 已如实披露的 5 项数据偏差，不修饰）；
  3. 脚本纳入演示须知「真实数据来源」叙事：被问分类准确率时直接引用回测数字 + 样本量 52 的边界。
- **验收标准**：脚本单命令可复跑（`python3 scripts/backtest_classification.py`），产物含两个维度完整混淆矩阵；报告章节数字与脚本输出逐位一致；明确写出「样本量 52、历史数据集、非独立测试集」的边界声明。
- **工时估计**：0.5 人日。

### 措施 2.b 误报控制：4 层漏斗统计固化为指标章节

- **现状差距**：盘点报告 C 节——误报控制能力客观存在（`work buddy接力/backend/services/weibo_pipeline.py` 4 层漏斗：L1 去重 bigram Jaccard>0.85 → L2 辟谣 5 关键词 → L3 机器人识别 → L4 地理围栏震中 300km，`get_funnel_stats()` 可出统计），且演示页已展示 53,340→52 漏斗串（评测指标 §2.3 实测），但**没有以「误报控制」命名的指标章节**，评委视角看不到该能力的度量化表述；该补丁未合并主干（按既有背景采信）。
- **具体改动**：
  1. `outputs/评测指标.md` 新增 §2.6「误报控制（4 层过滤漏斗）」章节，含两张表：
     - **主漏斗逐层留存**（引自 `data/funnel.json`，评测指标 §2.3 已实测）：`53,340 原始 → 去重剔 12,743（另 2 条 2025-01-09 噪声）→ 40,595 → 关键词初筛 9,617 → 抽样 100 → LLM 甄别 100 次调用 0 失败 → 实质 65 → 精选 52`；
     - **4 层过滤职责表**（引自 weibo_pipeline 设计）：去重 / 辟谣（辟谣·谣言·不实·假消息·澄清 5 关键词）/ 机器人（话题标签>5、正文<5 字）/ 地理围栏（震中 300km），每层注明判定规则与剔除口径；
  2. 明确边界声明（防过度承诺）：4 层漏斗为工程过滤规则，**不等于谣言查全率**；社情信号与官方通报交叉验证仍为最终防线（无社情匹配区域如实显示「社情信号 ×0 · 依据官方通报」，复用合规文档 §六.1 原文）。
  3. 页面侧不新增组件（漏斗串已在页面展示且 `verify-t5`/`t27` 已断言），只在页脚图例（措施 1.5）补一句「社情经去重/辟谣/机器人/地理围栏四层过滤」。
- **验收标准**：章节含逐层留存数字与 `funnel.json` 逐位一致；4 层规则与 `weibo_pipeline.py` 代码逐条对应；边界声明在章节内可见。
- **工时估计**：0.2 人日。

### 措施 2.c 定位：如实披露词典定位法，以「定位覆盖率」替代无法计算的定位准确率

- **现状差距**：盘点报告 C 节——定位无 ground truth（坐标本身来自词典，无发帖真实定位），**定位准确率在原理上不可计算**；现状为词典 27 个地名硬编码坐标、命中即 `confidence=0.85` 固定值、未命中回退震中降为 0.4；评测指标报告无定位相关指标；热力图层无置信度展示（同措施 1.3）。
- **具体改动**：
  1. `outputs/评测指标.md` 新增 §2.7「地理定位：方法与覆盖率」章节，文案草案（可直接落地）：
     > **方法如实披露**：当前定位为**地名词典定位法**——27 个地名（缅甸 11 / 云南 13 / 泰国 2 / 其他 1，见 `work buddy接力/backend/services/nlp_service.py` LOCATION_DICT）硬编码坐标，命中即赋固定置信度 0.85，未命中回退震中坐标并降为 0.4。**因无发帖真实定位 ground truth，定位准确率不可计算，本项目不做该承诺**；以「定位覆盖率」替代度量。
     > **定位覆盖率** = 命中词典的帖数 / 52 条精选帖（附逐地名命中计数，复用评测指标 §2.3 已有的 `extracted_location` 原始计数表与同地异写归一说明）。
  2. 覆盖率数字由措施 2.a 同一脚本顺带产出（复用 §2.3 计数即可，无新开发）；
  3. UI 侧置信度展示并入措施 1.3（热力图层标注 0.85/0.4 口径）。
- **验收标准**：章节含「准确率不可计算」的明确表述与原因；覆盖率数字与 `social_posts.json` 重算一致；页面热力层置信度标注与章节口径一致。
- **工时估计**：0.25 人日。

### 措施 2.d 信息时效：weibo 真实通道「系统拾取延迟」基线（依赖体验包，2026-09-04 前必须完成）

- **现状差距**：盘点报告 C 节——评测指标的时效章节**全是系统延迟，不是信息新鲜度**；`live_feed.py` 中 weibo 真实帖 `offset_min` 恒为 null（无震后偏移口径）。但字段基础已具备：`created_at`（多格式解析归一北京时间）与 `polled_at` 均已在输出契约中。
- **具体改动**：
  1. `live_feed.py` weibo 分支为每条帖新增字段 `pickup_latency_min = polled_at − created_at`（分钟，拾取时刻减发布时间；`created_at` 解析失败则置 null），并在 `/live/social` 响应顶层附 `latency_stats: {n, median_min, p90_min}`；改动约 10 行，不影响既有契约（仅增字段）；
  2. 体验包有效期内（≤2026-09-04）执行基线采样：`python3 live_feed.py --mode weibo` 实调，留档采样输出至 `outputs/weibo_probe/10_pickup_latency_baseline.json`（补齐探针记录链，与既有 01–06 号记录同目录）；
